ROLE
----
Act as a Senior Quantitative Developer, Python Engineer, Data Engineer
and Machine Learning Engineer.

You are building ANJANEYA: a research and backtesting system for NIFTY50
and NIFTY50 options using Zerodha Kite Connect API as the primary data
source.

This is NOT a live trading system. This is NOT a broker execution system.

The system has four long-term goals:

1. Fetch NIFTY index history from Zerodha.
2. Capture NIFTY options market data LIVE, day by day, and build our own
   historical dataset over time (Zerodha does not provide historical
   expired-option data, so we must accumulate it ourselves).
3. Compute a rich feature set: NIFTY trend/regime, option trend,
   candle behaviour, support/resistance, market structure, option
   Greeks/IV/OI, and relative behaviour.
4. Answer these SPECIFIC research questions using accumulated data:

   RQ1. How do NIFTY weekly options behave on expiry day vs start of
        expiry cycle vs mid-cycle?

   RQ2. Which time windows between 09:15 and 15:15 IST produce the most
        favourable risk-adjusted behaviour for CE vs PE?

   RQ3. Do time-of-day, day-of-week, and days-to-expiry interact with
        NIFTY regime and candle behaviour in a predictive way?

   RQ4. Can an ML model trained on the above features produce
        statistically meaningful predictions of future short-horizon
        behaviour, after transaction costs?

Everything must be measured. Nothing must be assumed.

============================================================
2. ARCHITECTURE — ANJANEYA'S 3 STANDALONE APPS
============================================================

ANJANEYA is NOT one giant Python file.
ANJANEYA is NOT a heavy microservices or 3-tier web architecture.

ANJANEYA is THREE small, focused Python applications that share a
common core library and a common local database. Each app can be
started, stopped, and debugged independently. They communicate only
through the filesystem / database, never through HTTP or a message
broker.

APP 1 — ANJANEYA-CAPTURE
------------------------
Purpose: fetch and store raw market data.
Runs: continuously during market hours (09:15–15:30 IST).
Responsibilities:
  - Refresh Zerodha access token automatically each morning (TOTP login).
  - Download NIFTY index historical OHLCV (backfill + daily top-up).
  - Connect to KiteTicker WebSocket.
  - Subscribe to NIFTY index, NIFTY futures, and the configured option
    universe (ATM ± N strikes, current weekly expiry, next weekly expiry).
  - Store every tick in a local database (DuckDB or Parquet).
  - Poll the option chain periodically for OI/IV snapshots (rate-limited).
  - Log every API call, every reconnect, every gap.
  - Handle disconnections with exponential backoff.
  - Never drop a tick silently.

APP 2 — ANJANEYA-ENGINE
-----------------------
Purpose: transform raw ticks/history into candles and features.
Runs: every N minutes during market hours + once after close.
Responsibilities:
  - Build OHLCV candles from stored ticks (configurable timeframe).
  - Compute all indicator engines (NIFTY trend, option trend, candle,
    levels, structure, S/R, Greeks, option context).
  - Assemble the unified feature table.
  - Validate features.
  - Write features to the feature store.

APP 3 — ANJANEYA-AI
-------------------
Purpose: train, predict, backtest, and report.
Runs: daily (after close) and on-demand.
Responsibilities:
  - Build ML datasets from features + labels.
  - Train model using purged walk-forward validation.
  - Generate predictions.
  - Run backtests with realistic Indian transaction costs.
  - Produce time-of-day / day-of-week / days-to-expiry analysis.
  - Generate charts, reports, feature importance.
  - Archive model versions and run metadata.

SHARED CORE LIBRARY
-------------------
A `core/` package imported by all three apps. Contains pure logic only
(no I/O side effects at import time):
  - indicators, nifty engine, options engine, price_action engine,
    features, ml utilities, backtest math, market calendar, config
    loader, logging helpers, data schemas, validation.

Each app has its own `run.py` entry point. Shell scripts in `scripts/`
handle scheduling (cron / Windows Task Scheduler / manual start).

4. ZERODHA KITE CONNECT — DATA STRATEGY
============================================================

CRITICAL FACTS YOU MUST DESIGN AROUND:

4.1 What Zerodha Provides
- Historical OHLCV (REST) for NIFTY index, NIFTY futures, active
  (unexpired) option contracts, equities.
- Historical OHLCV is NOT available for expired option contracts.
  Zerodha's official position: do not query expired instruments.
- WebSocket (KiteTicker) streaming for up to 3,000 instruments per
  connection, up to 3 connections per API key.
- REST /quote endpoints: ~1 req/sec, up to 500–1000 instruments per
  call. Not suitable as a live feed — use WebSocket.
- Historical candle rate limit: ~3 requests/sec.
- Other endpoints: ~10 requests/sec.
- OI is available in historical candle responses when `oi=1`.

4.2 ANJANEYA's Data Strategy
- NIFTY index history: fetched from Zerodha (historical API).
- NIFTY options history: BUILT BY ANJANEYA-CAPTURE, captured live, day
  by day, from WebSocket ticks + periodic option chain snapshots.
- This means the options dataset grows over time. ANJANEYA-AI must
  wait for enough accumulated days before training a serious model.

4.3 Data Accumulation Milestones
ANJANEYA must track and report data coverage. Suggested gates:
- 20 trading days captured → first exploratory analysis allowed.
- 60 trading days captured → first ML model training allowed.
- 120+ trading days captured → statistically meaningful backtests.
- 250+ trading days captured → seasonality and regime analysis.

These thresholds are configurable. ANJANEYA-AI MUST refuse to train a
"production" model below the configured minimum and must clearly label
any preliminary results as PRELIMINARY / EXPLORATORY.

4.4 Authentication
Zerodha requires daily login. Implement:
- TOTP-based automated login (pyotp)
- request_token → access_token exchange
- token persistence with daily refresh
- clear failure logging, retry policy
- credentials ONLY from environment variables or .env (never in code)

4.5 Rate Limiting
Implement a token-bucket rate limiter for every REST endpoint used.
Log every 429 response. Never retry without backoff.

4.6 Tick Storage Schema (minimum)
Each tick row: timestamp (UTC + IST), instrument_token, tradingsymbol,
last_price, volume_traded, oi, bid, ask, bid_qty, ask_qty, source.
Store append-only. Never overwrite captured ticks.

4.7 Candle Builder Rules
- Built strictly from stored ticks.
- Never mix ticks from different contracts.
- Handle first candle of day, last candle, missing ticks, zero-range.
- Store candles in a separate table/file from ticks.
- Support multiple timeframes in parallel (1m, 3m, 5m, 15m).

============================================================
8. NIFTY TREND ENGINE
============================================================

Full MA combinations calculated on NIFTY index only.

COMBINATION 1:
EMA 8 Low, EMA 8 High, SMA 108 High, SMA 180 High,
EMA 254 Close, SMA 720 High, SMA 1080 Close, SMA 2056 High

COMBINATION 2:
EMA 8 Low, EMA 8 High, EMA 144 High, SMA 89 High,
EMA 55 Close, EMA 360 High

COMBINATION 3:
EMA 20 Close, EMA 200 Close

For every relevant MA compute:
- price above/below
- MA slope
- normalized slope: (MA[t] - MA[t-k]) / (ATR[t] * k)
- MA alignment
- MA separation/spread: (fast_MA - slow_MA) / ATR
- spread velocity: spread[t] - spread[t-k]
- persistence

All k values configurable.

============================================================
9. NIFTY TREND SCORES AND REGIME
============================================================

Scores: fast_score, medium_score, long_score, composite_trend_score.

Initial weights (configurable, NOT optimal):
fast 0.40, medium 0.35, long 0.25.

Also compute: trend_acceleration, trend_persistence.

Regime states:
STRONG_BULLISH, BULLISH, BULLISH_DEVELOPING, NEUTRAL,
BEARISH_DEVELOPING, BEARISH, STRONG_BEARISH.

Do NOT emit BUY/SELL from this engine. It describes conditions only.

============================================================
10. OPTION TREND ENGINE
============================================================

Lightweight, applied per option contract.
Do NOT apply NIFTY long-period MAs to weekly options.

MAs: EMA 8 Low, EMA 8 High, EMA 20 Close, EMA 55 Close, EMA 200 Close
(all configurable).

Compute:
option_ma_alignment, option_ma_slope, option_normalized_slope,
EMA20_EMA200_spread, spread_velocity, ATR, momentum, trend_persistence.

Handle insufficient history explicitly (weekly options often lack
enough candles for EMA 200). Configurable behavior: flag / skip / use
shorter window.

============================================================
11. CANDLE BEHAVIOUR ENGINE
============================================================

For every candle compute:
body, range, upper_wick, lower_wick,
body_ratio, upper_wick_ratio, lower_wick_ratio, direction.

body       = abs(close - open)
range      = high - low
upper_wick = high - max(open, close)
lower_wick = min(open, close) - low

Protect against division by zero.

Numerical relationships with previous candle:
gap, engulf_ratio, inside_flag, outside_flag, body_ratio_change,
wick_ratio_change, close_position_within_prev_range.

Detect (numerically, not only by name):
strong bullish/bearish, small body, long wick, inside, outside,
bullish engulfing, bearish engulfing, rejection, breakout.

Store the numeric measurements as ML features — names are secondary.

============================================================
12. DAILY AND PREVIOUS-DAY LEVELS
============================================================

For every contract and NIFTY compute:
today_open, today_high, today_low, today_close,
previous_day_close, previous_day_high, previous_day_low,
previous_day_open.

Distance features (ATR-normalized where appropriate):
distance_to_today_high, distance_to_today_low,
distance_to_previous_day_high, distance_to_previous_day_low.

STRICT RULE: at timestamp T, "today_high" means the running high up to
T, not the day's final high. Same for low. Previous-day values must be
computed only from days fully closed before T.

This rule is non-negotiable and must have a dedicated leakage test.

============================================================
13. PRICE LEVEL INTERACTION ENGINE
============================================================

Event/state engine for important levels.

States:
NOT_TESTED, APPROACHING, TOUCHED, CROSSED_ABOVE, CROSSED_BELOW,
CLOSED_ABOVE, CLOSED_BELOW, HELD_ABOVE, HELD_BELOW, REJECTED,
RETESTED, FAILED_BREAKOUT, FAILED_BREAKDOWN.

Example (Previous Day High = 150):
149 → 151 → 152 → 151 → 153
Must detect: approach, touch, cross above, close above, hold above,
retest, continuation.

Example:
149 → 151 → 148 → 147
Must detect: break above, rejection, failed breakout, back below.

Equivalent logic for support.

Each event is timestamped and non-repainting.

============================================================
14. SUPPORT AND RESISTANCE ENGINE
============================================================

Candidate levels from:
previous day high/low, today high/low (running), previous close,
today open, recent swing highs/lows, local extremes.

For each candidate compute:
number_of_touches, rejection_count, breakout_count,
failed_breakout_count, breakdown_count, failed_breakdown_count,
retest_count, distance_from_current_price, reaction_strength.

Then compute configurable numerical support_strength and
resistance_strength.

These are analytical features. Do not auto-convert into trading signals.

============================================================
15. MARKET STRUCTURE ENGINE
============================================================

Detect Higher High, Higher Low, Lower High, Lower Low using
configurable swing detection.

Structural states:
BULLISH_STRUCTURE, BEARISH_STRUCTURE, RANGE, TRANSITION.

Also compute:
current_swing_high, current_swing_low,
distance_from_swing_high, distance_from_swing_low.

Swing confirmation delay must be explicit. A swing is only "known" once
enough subsequent candles exist. This constraint must be enforced in
feature generation — never use a swing that would only be confirmed in
the future.

============================================================
16. OPTION CONTEXT ENGINE
============================================================

For each option compute:
option_type, strike, expiry, days_to_expiry, distance_from_atm,
expiry_cycle_phase, time_of_day_bucket.

If available:
IV, IV_change, delta, gamma, theta, vega, OI, OI_change, volume.

If Zerodha does not provide Greeks, compute them internally using
Black-Scholes (European, cash-settled). Document model, risk-free rate
source, and dividend assumption.

Relative behaviour:
ExpectedOptionMove = Delta * NIFTYMove
ActualOptionMove   = option_price[t] - option_price[t-1]
OptionResidual     = ActualOptionMove - ExpectedOptionMove

Document limitations of this approximation.

20. LABELS
============================================================

Do NOT train the model to output BUY/SELL directly.

Predict future behaviour over configurable horizons (5, 10, 15, 30
minutes; multiple horizons supported):

future_return, future_max_up_move, future_max_down_move,
future_trend_change.

Classification labels (configurable thresholds, ATR- or
volatility-normalized):
UP_CONTINUATION, DOWN_CONTINUATION, RANGE, REVERSAL.

Strict separation between feature generation and label generation.
Labels must never appear as features.

============================================================
21. ML MODEL
============================================================

Start with LightGBM (fallback: XGBoost).
Model outputs class probabilities.

Components:
- dataset_builder
- splitter (purged walk-forward with embargo = max horizon)
- trainer
- predictor
- evaluator
- explainer (native importance, permutation, SHAP optional)

Add probability calibration metrics: log loss, Brier score,
reliability curves.

Compare against naive baselines:
- always-up
- always-range
- random
- NIFTY-regime-only

Keep the interface generic so a future model can be swapped in.

============================================================
22. TIME-SERIES VALIDATION (MANDATORY)
============================================================

Never shuffle financial time-series data.

Use PURGED WALK-FORWARD VALIDATION with an embargo equal to the maximum
label horizon. All scaling, encoding and feature selection must be fit
on training folds only.

Keep a final untouched holdout period. Never touch it during tuning.

Document every split precisely, including exact timestamps.

============================================================
23. BACKTESTER
============================================================

Only build the backtester after the feature engine is stable.

Support:
entry, exit, stop loss, target, time-based exit,
transaction cost, brokerage, slippage, bid/ask spread.

Execution model:
- signals generated at candle close T
- execution at T+1 open or bid/ask (configurable)
- configurable latency

Indian cost model:
brokerage, STT, exchange charges, GST, stamp duty, SEBI charges,
slippage, plus optional bid/ask spread from captured data.

Trade record includes:
timestamp, option, expiry, strike, option_type,
entry_price, exit_price, entry_reason, exit_reason,
NIFTY state, option state, candle state,
support/resistance state, AI prediction, AI probabilities,
P&L, MFE, MAE, holding_time, time_of_day_bucket, expiry_cycle_phase.

Never hide losing trades.

============================================================
30. NO LOOK-AHEAD BIAS RULE
============================================================

At timestamp T, only information available at or before T may be used.

- Do not use today's final high at 10:00 if it happened at 14:30.
- Do not use today's final low before it happened.
- Do not use future swing confirmation as if it were known earlier.
- Do not use future option prices.
- Do not include label fields as features.

Feature generation and label generation must be physically separated in
code and in the resulting datasets.

35. RESEARCH MINDSET
============================================================

The purpose of ANJANEYA is to discover whether NIFTY regime,
option trend, candle behaviour, support/resistance, market structure,
Greeks/IV/OI, and relative option behaviour — taken together — contain
useful predictive information for NIFTY weekly options.

Do not assume any feature is profitable.
Do not assume any MA combination is optimal.
Do not assume any candle pattern is predictive.
Do not assume support/resistance "works."
Do not assume any time-of-day is best.

Measure everything. Report honestly, including negative results.
